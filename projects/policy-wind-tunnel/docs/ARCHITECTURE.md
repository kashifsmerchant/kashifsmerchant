# Architecture

## Purpose

Policy Wind Tunnel compares approved policy expectations with several implementation profiles. Decision Replay exposes the case facts, applicable policy, and rule trace behind a result, and allows a repair to be examined under controlled conditions.

This release is a deterministic reference environment. The names “support agent,” “refund API,” and “reviewer procedure” identify reference implementations inside the demo. They are not connected external systems.

## Components

| Component | Responsibility |
| --- | --- |
| `fixtures.mjs` | Supplies repeatable fictional scenarios and case facts |
| `engine.mjs` | Validates policies, evaluates cases, and compares implementations |
| `app.mjs` | Applies user choices, renders results, handles imports and exports, and manages replay interactions |
| `index.html` and `styles.css` | Accessible application structure and responsive presentation |
| `about.html` and `about.css` | Independent public project profile |
| `tests/engine.test.mjs` | Behavioral assertions around consequential policy boundaries |

The core engine has no DOM or network dependency. The same JavaScript module can run in a browser or Node.js.

## Policy contract

```js
{
  version: "2.0",
  windowDays: 45,
  effectiveDate: "2026-11-01",
  allowPartial: true,
  maxAutoAmount: 150,
  requireReceipt: true
}
```

The baseline policy is version `1.0`. The intended expectation selects the baseline for purchases before the proposed policy’s effective date. A deliberately defective implementation can ignore this date, allowing the demo to expose a historical-case regression.

Policy validation should reject unsupported or incoherent configuration instead of quietly coercing it into a plausible result.

## Case contract

Each case records a stable case ID, fictional customer and order identifiers, purchase and request dates, amount, item counts, receipt evidence, item condition, and an optional note.

Case validation separates an invalid collection structure from incomplete decision evidence. An invalid top-level collection cannot be evaluated. A case with unavailable evidence can remain visible with an unknown outcome.

Dates are interpreted as UTC calendar dates, without introducing the viewer’s local timezone into elapsed-day calculations.

## Decision contract

```js
{
  decision: "approve", // approve | deny | review | unknown
  reason: "Human-readable outcome explanation",
  ruleId: "stable-rule-identifier",
  applicableVersion: "2.0",
  days: 35,
  amount: 64,
  trace: [
    {
      rule: "stable-rule-identifier",
      label: "Rule description",
      passed: true, // true | false | null
      value: "Observed fact",
      expected: "Required condition",
      evidence: "Source or fact description"
    }
  ]
}
```

Trace entries explain the rules actually evaluated. They are generated by deterministic execution and do not purport to reconstruct a language model’s private reasoning.

## Cross-implementation comparison

`evaluateSuite` computes:

- The baseline decision for each case.
- The intended result under the proposed policy and its effective date.
- Each implementation profile’s result.
- A list of implementations whose decision differs from the intended result.
- Whether the intended result changed from baseline.
- Whether required evidence was unavailable.
- Aggregate counts and per-implementation disagreement totals.

A policy outcome change can be intended. An implementation disagreement is a different finding. A stale policy version should remain inspectable even when it happens to return the same outcome for the selected case.

Aggregate counts describe the supplied case set. They do not imply a production error rate or financial impact.

## Repair and replay

The demo supports a broad repair that applies the latest policy everywhere, and a correct repair that also preserves effective-date semantics. The comparison suite should expose the historical cases that the broad repair mishandles.

A replay should preserve or explicitly identify its case facts, policy configuration, implementation profile, and execution mode. Its visible result should identify whether it is the original run or a newly evaluated branch.

The engine cannot reproduce an external state that was never recorded. A future live adapter must distinguish reconstruction from a new execution and mark missing evidence.

## Boundary for a future live adapter

A live integration should implement an explicit adapter boundary:

```js
async function evaluateImplementation({ caseRecord, policy, context }) {
  return {
    decision: "review",
    reason: "Explanation supported by recorded evidence",
    evidence: [],
    implementationVersion: "identified-version",
    executionMode: "live"
  };
}
```

The actual result must be compared with an independently approved expectation. A model-generated answer should not silently become both the implementation and its acceptance test.

For recorded responses, match the original tool request and relevant state before reuse. A new branch may require new simulated responses. If those are unavailable, report that the branch cannot be replayed faithfully.

Live integrations need their own authentication, permission boundaries, retention policy, timeout and retry behavior, and evaluation coverage. None is implied by the credential-free demo.

## Publication boundary

Public source includes the independent application, fictional fixtures, tests, and relevant documentation. Exclude credentials, runtime secrets, private business records, and unrelated source repositories.

Deployment and automation identifiers belong in the release registry maintained by the owning build agent. The public profile should link only to verified products in this series.
